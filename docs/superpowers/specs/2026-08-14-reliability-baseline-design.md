# dedao-gui 可靠性基线优化设计

- 日期：2026-08-14
- 状态：用户已确认
- 基线：`main@e486c2ccf108355d6971b4d9dbb0280782d33c8c`
- 目标平台：macOS、Windows、Linux

## 1. 背景

当前版本功能覆盖较完整，但代码审计发现四类问题已经影响安全性和下载正确性：

1. `backend/services/service_test.go` 提交了真实 Cookie、Token 和个人信息，并进入公开 Git 历史。
2. 下载器构造了 `Range` 请求头，却没有把该请求头传入实际 HTTP 请求；续传或分块下载可能重复追加整文件。
3. 电子书章节并发下载会由多个 goroutine 同时写共享错误变量和共享切片，存在数据竞争、乱序和内容丢失风险。
4. 发布流程没有测试质量门，Wails CLI 使用浮动的 `@latest`，版本号、校验文件和 macOS 签名状态也没有形成一致的证据链。

本期采用“可靠性基线”路线：先修复安全和下载正确性，再补足可重复测试与三平台发布门。首页重构、整体视觉改版和大规模文件拆分不属于本期。

## 2. 目标与非目标

### 2.1 目标

- 从当前代码和所有公开 Git 引用中移除已提交的敏感内容。
- 前端不再持有完整登录 Cookie；凭据仅由 Go 后端管理。
- 断点续传能够正确区分服务器支持、忽略或拒绝 Range 的情况。
- 下载结果在成功改名之前经过响应和文件大小校验。
- 电子书章节并发下载无数据竞争，输出顺序稳定。
- 配置文件损坏时能够备份、恢复并向用户说明实际状态。
- 核心测试不依赖真实账号、真实令牌或外网服务。
- macOS、Windows、Linux 使用同一套质量门和固定的构建工具版本。
- Git tag、应用内版本、发布资产名和 SHA-256 保持一致。

### 2.2 非目标

- 不重做首页、导航或整套视觉语言。
- 不新增课程抓取能力，不改变内容权限边界。
- 不重写全部下载业务和页面状态管理。
- 不在本期引入新的运行时第三方依赖。
- 不把平台签名证书、账号或公证凭据写入仓库。

## 3. 总体边界

运行时按四层划分：

1. **界面层**：展示登录状态、下载状态、错误原因和恢复动作，不保存完整 Cookie。
2. **会话层**：Go 后端结构化解析和保存必要 Cookie，统一判断登录是否有效。
3. **下载层**：一个 HTTP/Range 执行路径负责请求、响应校验、重试、取消和进度。
4. **落盘层**：先写 `.download` 临时文件，校验成功后再原子改名为目标文件。

测试和发布不绕开这些边界：测试使用本地 HTTP fixture 验证下载层；CI 只有在安全扫描、测试和三平台构建全部通过后才创建 Release。

## 4. 凭据与历史治理

### 4.1 当前代码

- 删除测试文件中的真实 Cookie、Token、手机号和用户资料。
- 原有线上接口测试改为显式的手工集成测试，默认不运行。
- 自动化测试改用 `httptest.Server` 和仓库内非敏感 fixture。
- 增加仓库内安全检查脚本，阻止 Cookie、JWT、手机号样例或已知敏感字段再次进入提交。

### 4.2 运行时凭据

- 前端只接收 `loggedIn`、用户展示信息和可操作状态，不接收完整 Cookie 字符串。
- 删除前端 LocalStorage 中的 `cookies` 数据来源；相关页面通过后端会话状态判断是否登录。
- 后端只保存业务确实需要的 Cookie 名值对，不保存 `Path`、`Domain`、`Expires` 等 `Set-Cookie` 属性。
- Cookie 值使用结构化 API 或 `strings.Cut`/`SplitN(..., 2)` 解析，禁止按所有等号无界拆分。
- 配置文件继续位于用户配置目录，Unix 平台保持仅当前用户可读写；Windows 使用用户目录继承 ACL。本期不引入系统钥匙串依赖，这一限制必须保留在风险说明中。

### 4.3 Git 历史重写

用户已经授权重写历史并强制推送。执行顺序必须是：

1. 创建只读镜像备份，记录当前分支、tag 和对象 ID。
2. 在临时镜像中清理所有分支和 tag 中的敏感内容。
3. 对全部引用执行敏感模式扫描，确认不再命中。
4. 记录重写后的分支、tag 和提交映射。
5. 明确目标远端后，强制推送已重写的分支和 tag。
6. 再从 GitHub 全新克隆并重复扫描，确认远端结果。

历史重写后旧提交 SHA 全部失效；已有本地克隆必须重新克隆，不能把旧历史合并回新仓库。受污染的本地镜像只作为受控回滚证据保存，不再推回公共远端。

## 5. 下载正确性

### 5.1 请求与续传

下载执行接口必须显式接收请求头和 `context.Context`。当临时文件已有 `N` 字节时：

- 发送 `Range: bytes=N-`。
- 只有收到 `206 Partial Content` 且 `Content-Range` 起点等于 `N` 时才允许追加。
- 如果服务器返回 `200 OK`，说明它忽略 Range；下载器必须截断临时文件并从零重新下载，禁止追加。
- 如果服务器返回 `416 Range Not Satisfiable`，只有在远端总大小与本地临时文件大小一致并通过校验时才可进入完成流程；否则清空临时文件并重新开始。
- 其他状态码作为结构化错误返回，不写入目标文件。

### 5.2 写入与完成

- 所有内容先写入同目录的 `.download` 临时文件。
- 每次写入检查返回字节数和错误，及时响应取消信号。
- 已知远端大小时，完成前校验最终文件大小。
- 校验通过后关闭文件，再把临时文件改名为目标文件。
- 失败时记录已写字节数、临时路径、是否可续传和原始错误。
- 自动重试有明确上限和退避，不对认证错误、权限错误或磁盘错误无限重试。

### 5.3 批量任务

- 并发数必须大于零，否则立即返回参数错误。
- 批量入口接收调用方上下文，取消时停止等待和未开始任务。
- `Acquire`、单任务错误和 `Wait` 错误必须传播到调用层。
- 单项状态仍然保留，整体结果提供首错和失败项统计。

## 6. 电子书并发

- 使用当前已有的 `golang.org/x/sync/errgroup` 管理章节请求和取消。
- 按章节数量预分配结果切片，每个 goroutine 只写自己的固定索引。
- 不允许并发 `append` 到共享切片，也不允许并发覆盖共享 `err`。
- 首个不可恢复错误取消同组剩余请求并向上返回。
- 最终内容严格按章节索引拼接，网络完成顺序不得影响输出顺序。

## 7. 配置与登录恢复

### 7.1 配置写入

- `Marshal`、`Seek`、`Decode` 和文件写入错误全部显式返回，禁止 `panic`、`log.Fatal` 或静默忽略。
- 采用“同目录临时文件 → 刷盘/关闭 → 备份旧文件 → 替换”的写入流程。
- 替换流程需要分别验证 Windows 与 Unix 的文件语义。

### 7.2 损坏恢复

- 空文件可初始化为空配置。
- 非空但无法解析的配置先复制为带时间戳的备份，再初始化空配置。
- UI 显示“配置已备份，需要重新登录”，并给出备份路径。
- 登录失效只清除失效会话，不删除下载目录或其他用户数据。

### 7.3 登录响应

- 使用 `resp.Cookies()` 等结构化来源处理多个 `Set-Cookie`。
- 401/403 标记会话失效；496 标记需要在官方网页完成验证码。
- 认证类错误不进入普通网络重试循环。

## 8. 最小界面变更

本期界面只承担可靠性反馈，不做视觉重构：

- 下载任务显示排队、下载中、校验中、完成、失败、已取消六类状态。
- 失败信息包含用户可理解的原因和下一步动作；详细系统错误可展开查看。
- 登录弹窗用按钮提供“重置登录状态”，危险命令只放在高级排障说明中。
- 首页已有 `loading` 状态接入可见的加载反馈；接口失败不再只写入控制台。
- 下载格式选择等与本期触达的交互改为可聚焦、可键盘操作的语义元素。

## 9. 错误处理规则

| 场景 | 状态 | 恢复策略 |
| --- | --- | --- |
| 断网或超时 | 失败，可重试 | 保留合法临时文件；支持 Range 时续传 |
| 服务器忽略 Range | 重新下载 | 截断临时文件，从零开始，不追加 |
| Content-Range 不匹配 | 失败 | 停止写入，提示响应不一致 |
| 401/403 | 登录失效 | 停止下载并引导重新登录 |
| 496 | 需要验证 | 引导用户在官方网页完成验证码 |
| 磁盘空间不足 | 失败 | 停止写入，显示目标路径和系统错误 |
| 目录无权限 | 失败 | 不重试，提示更换目录或修复权限 |
| 用户取消 | 已取消 | 取消上下文并关闭响应；保留可续传临时文件 |
| 配置损坏 | 已恢复 | 备份损坏文件，生成空配置并提示重新登录 |

## 10. 测试设计

### 10.1 后端离线测试

使用 Go 标准库 `httptest.Server` 覆盖：

- 正常 `200` 全量下载。
- 合法 `206` 续传。
- 服务器忽略 Range 并返回 `200`。
- `Content-Range` 起点错误。
- `416` 且本地大小正确或错误。
- 中途断线、超时和取消。
- 最终文件大小不符。
- Cookie 值包含等号、多个 `Set-Cookie` 和属性字段。
- 空配置、截断 JSON、只读目录和备份恢复。
- 电子书章节乱序完成但结果顺序稳定。

### 10.2 并发测试

- macOS 和 Linux 执行 `go test -race ./backend/...`。
- Windows 执行普通后端测试和完整应用构建。
- 测试不得访问真实得到接口，不得要求账号或人工输入。

### 10.3 前端验证

- `npm ci` 必须严格使用锁文件。
- `npm run build` 作为 TypeScript 与 Vite 构建门。
- 登录状态、下载状态和错误映射通过固定契约数据验证；如果实现需要新增测试工具，必须另行批准依赖。

## 11. 三平台发布门

发布按以下顺序执行，前一步失败时不得进入下一步：

1. 仓库敏感模式检查。
2. Go 后端离线测试与静态检查。
3. macOS/Linux 竞态检测。
4. 前端锁定安装和构建。
5. macOS、Windows、Linux 构建矩阵。
6. 启动或最小运行 smoke 检查。
7. 生成 SHA-256 并上传校验文件。
8. 创建 GitHub Release。

工具版本固定为项目声明值：Go 使用 `go.mod`，Wails CLI 与 `go.mod` 的 Wails v2 版本保持一致，Node 版本在仓库和 CI 中统一声明。`wails.json` 使用 `npm ci`，禁止直接构建时漂移 lockfile。

release tag 必须注入应用元数据。验收时比较：

- Git tag；
- macOS `CFBundleShortVersionString`；
- Windows 文件版本；
- Linux 资产名或构建元数据；
- Release 资产文件名和对应 SHA-256。

平台签名采用可选的受保护凭据 job。未配置证书时可以生成内部测试包，但公开 Release 必须明确标注“未签名”，不能暗示已经通过 Apple 或 Windows 信任链验证。

## 12. 实施顺序

1. 建立离线测试骨架，移除当前测试中的敏感内容。
2. 修复 HTTP 请求头传递、Range 响应校验和临时文件完成逻辑。
3. 修复电子书并发和批量任务错误传播。
4. 修复 Cookie 结构化处理与配置原子写入/恢复。
5. 调整最小 UI 状态与错误提示。
6. 固定构建工具并增加 CI/Release 质量门。
7. 在全部代码和测试通过后执行 Git 历史重写。
8. 全新克隆远端，完成三平台构建与发布证据复核。

历史重写安排在代码修复之后，避免同一轮工作重复改写远端历史。

## 13. 验收标准

- 当前工作树和所有重写后的 Git 引用均不含已知敏感内容。
- 前端存储中不存在完整 Cookie。
- 所有 Range 场景由离线测试覆盖，续传文件不重复、不超长、不静默损坏。
- `go test -race ./backend/...` 在支持平台无数据竞争。
- 配置损坏后保留备份，应用可启动并提示重新登录。
- `npm ci` 和 `npm run build` 通过且不修改锁文件。
- 三平台构建均通过同一质量门。
- tag、应用元数据、发布资产和 SHA-256 一致。
- macOS 实机能够启动，并能看到登录、下载、校验、失败和取消状态。

## 14. 回滚与剩余风险

### 14.1 回滚

- 历史重写前保留本地只读镜像和引用清单。
- 业务修复采用小提交，单个问题可以独立回退。
- 发布失败时回退业务提交；不得把含敏感内容的旧历史重新推回公共远端。
- 下载格式升级不修改用户已完成文件，只处理新任务和 `.download` 临时文件。

### 14.2 剩余风险

- 公开历史曾包含凭据和个人信息，重写 Git 历史不能撤回已经被第三方克隆的数据；相关凭据仍应视为永久失效。
- 本期不引入系统钥匙串，Windows 上配置文件安全依赖用户目录 ACL。
- 得到接口和风控行为属于外部依赖，离线测试只能验证客户端契约，不能保证未来接口不变。
- Apple 公证和 Windows 代码签名需要外部证书与受保护凭据；没有这些材料时只能验证未签名构建。
